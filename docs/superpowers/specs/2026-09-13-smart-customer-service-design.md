# 智能客服 MVP 设计规格

日期：2026-09-13

## 目标

构建一个面向学习 Agent 应用的 Web 智能客服最小闭环。系统必须完整演示：实时对话、知识库检索、DeepSeek 工具调用、转人工、客服接管，以及一次会话的可回放 Agent 轨迹。

该版本是可运行的学习原型，不是生产客服平台。

## 已确认范围

### 包含

- 单一 Web 渠道，提供实时流式对话。
- DeepSeek 作为聊天模型与函数调用模型；密钥仅配置在服务端环境变量。
- 本地嵌入模型生成中文文档向量，并在应用内完成向量相似度检索。
- 三类工作区：客户、客服、管理员。
- 知识库 FAQ/Markdown 文档的导入、切分、索引与检索。
- 一个只读的模拟订单查询工具。
- 用户主动转人工，以及检索不足或模型无法处理时的自动转人工。
- 会话、工单和 Agent 运行轨迹的持久化与管理员回放。

### 不包含

- 真实退款、支付或订单修改操作。
- 微信、电话、邮件等多渠道接入。
- 真实用户注册、企业 SSO、细粒度权限体系。
- 多 Agent 协作、语音能力、自动质检和高级报表。
- 真实客户隐私数据。

## 技术方案

在 `D:\AI\smart-customer-service` 新建独立 TypeScript 项目。

- 前端：React、Vite、TypeScript。
- 后端：Node.js、TypeScript；提供 HTTP API 与 SSE 流式响应。
- 数据库：SQLite；向量以文档块元数据一并保存，MVP 在应用层计算相似度，无需独立向量数据库。
- 模型：DeepSeek OpenAI 兼容 API。后端以 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 与 `DEEPSEEK_MODEL` 配置；浏览器不接触 Key。
- 嵌入：本地运行的中文嵌入模型。模型下载和加载封装在嵌入模块，不依赖第二个云端密钥。

后端按模块组织，而非拆成多个服务：会话、Agent 编排、知识库、订单工具、工单、运行轨迹和管理 API 均有独立边界。

## 路由与角色

| 路由 | 角色 | 责任 |
|---|---|---|
| `/chat` | 客户 | 发起会话、接收流式回答、查看引用、转人工、提交评价。 |
| `/agent` | 客服 | 查看待接管队列、接管会话、人工回复、关闭工单。 |
| `/admin` | 管理员 | 管理知识库、浏览会话、回放 Agent 运行轨迹。 |

第一版采用固定演示身份，不做完整登录。客户通过浏览器生成的访客标识关联会话；客服与管理员页面使用预置演示角色。

## 会话状态与数据流

```text
客户发送消息
  → 保存消息与会话状态
  → Agent 编排
      → 检索知识库
      → 需要订单信息时调用只读订单工具
      → DeepSeek 生成流式回答并返回引用
  → 保存 Agent 运行记录
  → SSE 推送客户界面

若用户请求人工、检索无可靠结果或 Agent 无法处理
  → 创建工单
  → 会话转为“等待接管”
  → 客服接管后转为“人工处理中”
  → 客服关闭工单后会话结束
```

会话状态为：`ai_processing`、`ai_replied`、`waiting_human`、`human_active`、`resolved`。

转人工是单向控制权转移：一旦转入 `waiting_human`，机器人不再对新消息生成回复；客服接管后拥有唯一回复权。第一版不支持将会话再交回 Agent。

## Agent 编排规则

1. 每条客户消息创建一个 Agent 运行记录。
2. 从会话历史和当前消息构建上下文；对知识库检索得到候选文档块。
3. 如候选内容达到配置的相关性阈值，将最相关片段与来源传入 DeepSeek。
4. 向 DeepSeek 提供 `query_order` 工具。只允许查询模拟订单数据；后端校验所有工具参数，再执行调用。
5. 模型可以生成回答或请求调用工具。工具结果返回模型后，模型生成最终答案。
6. 若没有可靠检索结果、模型明确无法回答、工具失败，或用户主动要求人工，则创建转人工工单而非编造答案。
7. 客户看到的回答须包含可点击/可显示的知识来源标记；订单查询结果不应泄露预设数据外的信息。

工具调用与模型响应的超时、无效参数、API 错误必须被结构化记录。界面向客户显示简短、可理解的失败提示，并提供转人工入口；不得暴露 Key、堆栈或模型内部错误。

## 知识库

- 管理员导入 FAQ 或 Markdown 文档。
- 服务将文档切为带来源信息的文本块，生成并保存向量。
- 每个文档块保留文档标题、原始路径/标识、文本、创建时间和索引状态。
- 检索返回前若干候选块及相似度；仅通过阈值的块才能作为回答依据。
- 管理员可查看已导入文档与索引状态；删除、重建索引、复杂版本管理留到后续版本。

## 主要数据

| 实体 | 关键字段 | 用途 |
|---|---|---|
| 会话 | id、访客标识、状态、控制者、创建/关闭时间 | 驱动聊天与控制权。 |
| 消息 | id、会话、角色、正文、时间 | 完整会话记录。 |
| 工单 | 会话、转人工原因、接管客服、状态、关闭时间 | 人工处理闭环。 |
| 知识文档/块 | 文档元数据、文本、向量、索引状态 | RAG 检索。 |
| Agent 运行记录 | 会话、触发消息、模型、状态、耗时、token 用量、失败原因 | 回放与调试。 |
| 检索证据 | 运行记录、文档块、相似度、是否引用 | 解释回答依据。 |
| 工具调用 | 运行记录、工具名、脱敏参数、结果、状态 | 追踪工具行为。 |

API Key 不存入数据库。完整模型推理过程不记录。演示订单号等可识别字段在管理员回放中应按规则遮罩。

## 管理员回放

管理员选中会话后，需能按时间查看：

- 客户、AI、客服与系统消息；
- 每次 Agent 运行的状态、模型、耗时与 token 用量；
- 使用的知识库片段、相似度和答案引用；
- 订单工具的调用和结果；
- 转人工的原因、接管情况和工单生命周期。

## 验收场景

1. 客户询问 FAQ，系统检索知识库并流式回答，且标出来源。
2. 客户询问模拟订单状态，Agent 调用 `query_order` 后返回结果。
3. 客户询问超出知识库的问题，系统不臆造并转入人工队列。
4. 客户主动转人工后，客服在 `/agent` 接管；此后仅客服回复。
5. 管理员在 `/admin` 回放上述会话，能看到检索、工具调用、转人工原因和会话状态变迁。
6. DeepSeek Key 缺失、模型超时或工具参数无效时，系统不泄露敏感信息，明确告知客户并给出转人工路径。

## 测试策略

- 单元测试：状态机、转人工规则、工具参数校验、相似度阈值和订单工具。
- 集成测试：文档索引、Agent 编排、DeepSeek 适配器的模拟响应、会话/工单持久化。
- 端到端测试：三个验收主路径与管理员回放。
- 手工验证：使用真实 DeepSeek Key 验证流式对话和工具调用；密钥只通过环境变量注入。

## 后续扩展

完成 MVP 后，优先增加真实身份认证、更多业务工具、文档重建索引、会话指标与多渠道接入。多 Agent 仅在单 Agent 编排已经难以维护时再引入。
